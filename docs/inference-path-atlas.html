01The route table all three share

Same HTTPRoute/kserve-mock, same sixteen rules, same names, in all three clusters. That is the point of the comparison: the routing semantics are held constant so the difference between the stacks is the policy chain around them, not the matcher.

An OpenAI client names its model in the JSON body. Gateway API matches on paths and headers. The bridge is the Gateway API Inference Extension body-based router (BBR): it reads body.model, writes it into the internal x-gateway-model-name header, and clears Envoy's route cache so the match runs again against the header it just set.

So the twelve model mappings in eleven pool rules below are unreachable on the first pass and decisive on the second. Five unheadered rules cover chat, embeddings, rerank, transcription, and the final /v1 fallback. The two rerankers share one rule because Gateway API caps an HTTPRoute at sixteen rules. Multipart audio has its own named section because BBR parses JSON only; every transcription model is small-tier and uses ordinary route-wide membership authorization.

  4. 2model-deepseek-v4-proPOST /v1/chat/completions + deepseek-v4-prokserve-b300

A second HTTPRoute/keycloak carries /realms to the Keycloak service on the same listener, so token issuance and inference share one port and one Gateway. Envoy sorts it between the model rules and the /v1 prefix rule by ordinary Gateway API precedence — longer path first, header matches before bare paths.

Envoy AI Gateway carries one route the other two do not: AIGatewayRoute/kserve-mock-ai, pinned to the ai.local hostname. It exists only so the AI Gateway processor can parse the response and publish token counts as dynamic metadata; everything else stays on the shared route.

02Envoy AI Gateway

11 HTTP filters · read from /config_dump on ai-demo/ai-gateway/http

Everything is a typed Gateway API policy, and the resulting Envoy filter chain is legible: authenticate, transform, authorize, meter, pick an endpoint. Authentication happens before any external processor runs, and authorization happens after — which is exactly what lets the RBAC rules match a header BBR invented.

  1. 1
    envoy.filters.http.cors SecurityPolicy · .cors

    Preflight is answered here and goes no further. A live OPTIONS from the allowed origin returned 200 with the three access-control-allow-* headers and an empty body.

    +access-control-allow-origin: https://console.example.com (response, preflight only)
    +access-control-allow-methods: GET, POST, OPTIONS
  2. 2
    envoy.filters.http.jwt_authn SecurityPolicy · .jwt

    Verifies the Keycloak access token against the realm JWKS, cached five minutes. On success claimToHeaders flattens four claims into request headers — this is the only reason the rate limit descriptors downstream have anything identity-shaped to key on, because Envoy's limit actions match headers, never claims.

    The failure is a local reply, so nothing upstream is contacted.

    +x-user-id: alice ← preferred_username
    +x-auth-tier: big ← tier
    +x-org-id: acme ← org (tenant limits only)
    +x-team-id: research ← team (tenant limits only)
    ✕401 · www-authenticate: Bearer realm="…" · body "Jwt is missing"
  3. 3
    ext_proc/aigateway AIGatewayRoute · kserve-mock-ai

    Active on the ai.local virtual host only. On the response it parses the OpenAI usage object and writes the counts into dynamic metadata under io.envoy.ai_gateway, where the rate limit filter can charge them as a cost. It is the only reason a token budget is expressible on this stack at all.

    +metadata io.envoy.ai_gateway:llm_input_token / llm_output_token / llm_total_token
  4. 4
    ext_proc/…/model-body-router-chat/extproc/0 EnvoyExtensionPolicy

    vLLM Semantic Router, first element of the ordered extProc list, attached to the chat sections only. The request body is buffered so the router can read the prompt; failOpen: true, so a router that is down leaves the request untouched.

    It resolves the auto aliases and forwards a concrete model name unchanged. A matched decision may also replace the system prompt.

    ~body.model: "auto" → "kimi-k3" decision big
    ~body.messages[0]: system prompt replaced
    +x-selected-model: kimi-k3 (request)
    +x-vsr-selected-decision / -model / -confidence / -matched-keywords (response)
  5. 5
    ext_proc/…/model-body-router-tasks/extproc/0 EnvoyExtensionPolicy

    The same BBR image, attached to the embeddings and rerank sections. Chat traffic skips it; the semantic router never sees an embeddings body, which is deliberate — the router implements OpenAI chat only.

  6. 6
    ext_proc/…/model-body-router-chat/extproc/1 Backend · body-based-router

    Body-based router, second element of the same chain, so it reads the body the semantic router just rewrote. It sets the internal routing header and clears the route cache. failOpen: false: pool selection is part of the serving path, not an optimisation.

    It is attached to the base chat section and to all five model sections, so a client-forged header is overwritten even when that header steered the first match. Measured: forging x-gateway-model-name: kimi-k3 with body.model: mock-kserve landed on the CPU pod.

    ~x-gateway-model-name: <forged or absent> → kimi-k3 ← body.model
    ↻route cache cleared → rule 12 (chat) re-matches to rule 0 (model-kimi-k3)
  7. 7
    envoy.filters.http.rbac SecurityPolicy · .authorization

    defaultAction: Deny and five first-match-wins rules. Because this sits after BBR, the rules can name x-gateway-model-name — a value no client can supply.

    One scalar claim implements a ceiling: big reaches every tier, medium reaches medium and small, and small reaches small only. Org and team are not consulted.

    1 big-tier Allow claim tier=big ∧ resolved tier=big
    2 deny-big-tier Deny resolved tier=big
    3 medium-tier Allow claim tier∈{big,medium} ∧ resolved tier=medium
    4 deny-medium-tier Deny resolved tier=medium
    5 small-tier Allow claim tier∈{big,medium,small}
    ✕403 · body "RBAC: access denied" medium ceiling requesting big
  8. 8
    envoy.filters.http.ratelimit BackendTrafficPolicy

    One filter, domain ai-demo/ai-gateway/http, counters in Redis. Seven rules compile to eight descriptor sets attached per route, and every set opens with a generic_key whose value is the route rule name.

    That first action is the whole story behind the doubled tenant ceiling: kserve-mock/rule/12 and kserve-mock-ai/rule/0 are different descriptors, so the same org gets one budget on each route. The alternative — shared: true — emits a second filter with a second domain and silently unhooks the token budget, which is why it is off here.

    +x-ratelimit-limit: 5, 5;w=60, 20000;w=86400, 100;w=60
    +x-ratelimit-remaining: 4 measured with x-rate-limit-probe: true
    +x-ratelimit-reset: 28
    ✕429 on request 6 of 8 · token budget 429 on request 3 of 6
  9. 9
    ext_proc/endpointpicker/<pool> InferencePool · KServe EPP

    One filter instance per InferencePool; the route's backend selects which one applies. KServe's llm-d endpoint picker chooses the replica and stamps the choice on the response.

    +x-session-token: <base64 pod identity> (response)
    +x-went-into-resp-headers: true
  10. 10
    header_to_metadata → router Envoy built-in

    Dispatch to the chosen pod. The response body is not rewritten by any gateway filter on the way back — the mock_* fields in it are the fixture describing what it received.

+ added ~ rewritten ✕ short-circuits here ↻ re-routes

03agentgateway

policy-phase ordering · not an Envoy proxy, so no filter dump to read

Five policies against one route plus one against the Gateway, all in a single CRD. The ordering that matters here is not a filter list but a declared phase — and this stack has exactly one external-processing slot per phase, which is the constraint the whole chat path is built around. See section 07.

  1. 1
    traffic.extProc · phase: PreRouting — chat arm AgentgatewayPolicy · model-body-router

    Targets the Gateway, not the route, and runs before a route is chosen. The conditional's first arm sends POST /v1/chat/completions to the semantic router, which resolves the auto aliases and forwards a concrete model unchanged.

    The method is part of the condition. Without it an OPTIONS preflight reaches a chat-only processor and is answered 405 before the CORS policy ever runs — measured, and fixed.

    ~body.model: "auto" → "kimi-k3" · system prompt replaced
    +x-selected-model: kimi-k3 (request) · x-vsr-* (response)
  2. 2
    traffic.extProc · phase: PreRouting — task arm same policy, second condition

    POST /v1/embeddings and /v1/rerank go to BBR instead, through a native AgentgatewayBackend with HTTP/2 and verification disabled — BBR mints a fresh self-signed certificate every start. The semantic router would answer these with a chat-only 404.

    Only one arm ever runs: the conditional is first-match-wins.

    ~x-gateway-model-name := body.model tasks only
  3. 3
    traffic.transformation · phase: PreRouting same policy, different field

    Chat never reaches BBR, so the routing header comes from the router instead: x-gateway-model-name := x-selected-model. transformation is a different field from extProc, so it merges with the block above rather than replacing it.

    Verified on a live cluster that extProc runs before transformation within the phase — a probe transformation read a header the processor had just set.

    Conditional, with no fallback arm. An unconditional rule wipes the header BBR writes for the task paths; measured, bge-m3 fell from the l40s pool back to the shared CPU fixture.

    Both arms are scoped to the chat path, not just the second. x-selected-model is a header the router sets, but nothing stops a client sending one, and BBR does not strip it on the task paths — see section 09.

    ~POST /v1/chat/completions + x-selected-model → x-gateway-model-name
    chat with no selection → header cleared, so a forged value cannot survive
    tasks → neither arm matches, BBR's header preserved
  4. 4
    route selection HTTPRoute · kserve-mock

    The sixteen rules from section 01, matched once, against the header the phase above produced. There is no route-cache reset in this design because there was never a first pass to discard.

  5. 5
    traffic.jwtAuthentication · mode: Strict AgentgatewayPolicy · kserve-mock-jwt

    Keycloak issuer and audience, JWKS fetched through a backendRef rather than a URL. Strict means an unauthenticated request never reaches the InferencePool. Measured: 401.

    Nothing is exported from the token. The verified claims stay inside the proxy for CEL to read — which is why the pod sees no identity headers at all.

  6. 6
    traffic.authorization · action: Require kserve-mock-small-tier + …-medium-tier + …-big-tier

    Pure CEL over the verified claims — there is no claim-matching DSL. Three cumulative rules implement the same scalar tier ceiling. The big rule matches exactly the three B300 names, the medium rule matches deepseek-v4-flash, and the route-wide small rule covers every API including multipart transcription.

    Org and team are deliberately absent. Measured: a big-tier token reaches all three tiers, a medium-tier token reaches medium and small, and forging x-gateway-model-name: mock-kserve while asking for kimi-k3 still returns 403 because the transformation overwrites the header.

    jwt.tier ∈ {big, medium, small}
    resolved tier != medium || jwt.tier ∈ {big, medium}
    resolved tier != big || jwt.tier == big
    ✕403 · content-type text/plain · body "authorization failed"
  7. 7
    traffic.cors AgentgatewayPolicy · kserve-mock-cors

    Same origin allow-list as the Envoy stack, expressed as a traffic policy rather than a security one. Preflight measured at 200 — but only once the pre-routing conditions gained their method guard, since this now runs after them.

  8. 8
    traffic.rateLimit.conditional · local kserve-mock-rate-limit

    Counted inside the proxy: no Redis, no limit service. The cost is that the budget is per proxy instance and the coarsest local window is an hour, so a daily quota is not expressible without the external service.

    Nested org/team buckets are not expressible either, and the reason is the same first-match-wins rule that shapes the ext_proc chain above: only the first matching conditional policy executes, and that cannot charge an org counter and a team counter for the same request. Note that the authorization rules two hops up are cumulative — one API, two composition semantics.

    ✕429 on request 6 of 8 (5/min) · quota 3/hour, shared bucket
  9. 9
    InferencePool → KServe EPP → pod inference.networking.k8s.io

    Endpoint selection is identical to the other two stacks; the same x-session-token and x-went-into-resp-headers come back. Token-based limits are unavailable on this path: agentgateway's token units need one of its own AI backends with tokenization enabled, and a Gateway API InferencePool does not publish that metadata.

Scope note

Hops 5–8 are ordered by policy shape, not by a config dump

agentgateway is not Envoy, so there is no /config_dump to read the intra-route order off. Four boundaries were measured directly: ext_proc runs before routing (a forged header is overwritten and the pool changes), extProc runs before transformation within the phase, CORS runs after the pre-routing phase (the 405 above), and JWT runs before authorization (401 without a token, 403 with a valid one). The relative order of rate limit against the rest of the route phase is taken from the policy definitions.

04Kuadrant on Istio

11 HTTP filters · read from /config_dump on the OpenShift-profile Gateway

The one stack with no Gateway API surface for external processing, so both processors are raw EnvoyFilter patches. The consequence shows up in the ordering: Kuadrant's own policies all live in a single wasm filter near the end of the chain, which means every request is routed, transformed, and endpoint-picked before anyone checks who sent it.

  1. 1
    ai.gateway.semantic_router EnvoyFilter · semantic-router

    INSERT_FIRST. Disabled at the virtual host and re-enabled per route on the six chat rules, so task APIs and Keycloak bypass a chat-only processor instead of collecting its 404. A DestinationRule disables mTLS toward it, because the router terminates plaintext h2c and is not in the mesh — without that the handshake fails and, since the filter fails open, every request would quietly route as though no router were installed.

    ~body.model: "auto" → "kimi-k3" · system prompt replaced
    +x-selected-model (request) · x-vsr-* (response)
  2. 2
    istio.metadata_exchange Istio built-in

    Mesh telemetry. No effect on the request.

  3. 3
    ai.gateway.body_based_router EnvoyFilter · model-body-router

    INSERT_BEFORE the canonical ext_proc name, which is how it lands immediately ahead of KServe's endpoint picker. A distinct filter name is required: the EPP's per-route override would otherwise replace this filter's gRPC service.

    The per-route overrides are exact-name matches, so all fourteen JSON route names are enumerated by hand. The transcription and catch-all sections intentionally bypass BBR. That verbosity is the price of having no policy API for this.

    ~x-gateway-model-name := body.model ← the body the router rewrote
    ↻route cache cleared → re-matches to model-kimi-k3
  4. 4
    envoy.filters.http.ext_proc InferencePool · KServe EPP

    Endpoint selection — and note where it sits. On a request with no token at all, the measured 401 still carried an x-session-token, which is the endpoint picker's stamp. The pod was chosen before the caller was identified.

  5. 5
    grpc_stats · istio.alpn · fault · cors · istio.stats Istio built-in

    The CORS filter is present but unconfigured: no Kuadrant policy in this repository writes a CORS rule, and a preflight measures 405 rather than an allow-list. That is a real gap in the column, not a rendering of it.

  6. 6
    envoy.filters.http.wasm AuthPolicy + RateLimitPolicy + TokenRateLimitPolicy

    One filter carrying all of Kuadrant. Authorino verifies the token; a route-wide small rule, one H200/medium rule, and three B300/big model rules implement the same scalar tier ceiling. Org and team are used only by the separate tenant-limit probes.

    On success Authorino injects four identity headers toward the upstream. Limitador then counts, and the token budget charges usage.total_tokens off the response.

    +x-auth-user: alice · x-auth-tier: big · x-auth-org · x-auth-team
    ✕401 · x-ext-auth-reason: "a Keycloak access token is required; POST /realms/…"
    ✕403 · x-ext-auth-reason: "the token tier does not allow the resolved model tier"
    ✕429 · token budget spent on request 4 of 6 (100/min)
  7. 7
    router → pod Envoy built-in

    The upstream is reached last, on the endpoint chosen at hop 4.

Consequence of the ordering

The four injected identity headers cannot key a rate limit here

Authorino adds x-auth-org and x-auth-team toward the upstream, so they are not in request.headers when the rate limit action in the same wasm filter evaluates its CEL counters. Three keyings were measured against the nested tenant limits: auth.identity.* is unenforced, the injected headers are unenforced, and a client-supplied x-auth-org is enforced — and is therefore forgeable, which is not a tenancy control. The nesting row in the comparison reads unenforced for exactly this reason.

The auto_pools row in the repository's own comparison table had been recording the gap all along — b300 / h200 / h100 for Envoy and Kuadrant, all / all / all for agentgateway. 07The cost of one pre-routing slot

Fixing the agentgateway column meant working inside a hard limit: this stack has exactly one external-processing slot per phase per target, and two processors wanted it. What follows is what the API permits, what it silently permits, and the one trade-off that has no good answer.

There is no ordered chain

The Envoy stack solves this with a list — extProc: [semantic-router, bbr] — and each entry sees what the previous one wrote. agentgateway v1.4.1's traffic.extProc is a single object: one backendRef, or a conditional array the CRD documents as the first matching policy will be executed. One processor, either way.

Two policies do not help. Traffic policies merge field-level with precedence, so a second policy setting extProc replaces the first rather than chaining with it. That failure is quiet:

$ kubectl get agentgatewaypolicy model-body-router -o jsonpath='{…conditions}'
✓Accepted=True (Valid) Attached=True (Attached)
$ kubectl get agentgatewaypolicy kserve-mock-semantic-router -o jsonpath='{…}'
✓Accepted=True (Valid) Attached=True (Attached)
✕only BBR ran · model:auto reached the pod literally · HTTP 404

Both objects report healthy. Nothing names the processor that was dropped.

The shape that works

Give the slot to the router for chat, keep BBR on the JSON task paths, and carry the decision into the route table with a different field — transformation merges alongside extProc instead of replacing it.

Measured before building on itResult
Does transformation run after extProc?yes — a probe transformation read a header BBR had just set
Does the router emit x-selected-model for models outside its own catalog?yes — including glm-5.3 and deepseek-v4-pro
Is x-selected-model forgeable?no — a client-supplied value is overwritten
Can a forged x-gateway-model-name downgrade the authorization check?no — medium-tier caller still 403

Two regressions the happy path would have hidden

Both surfaced only from re-running the full comparison rather than checking that auto worked.

✕bge-m3 → CPU fixture unconditional transformation wiped BBR's header on task paths
→conditional, no fallback arm l40s restored
✕CORS preflight → 405 OPTIONS now reaches a chat-only processor before the CORS policy
→request.method == "POST" in the conditions 200 + allow-origin restored
The trade-off with no good answer

The router now owns a security-relevant name

Because the router resolves the model that selects the pool and that the tier-ceiling authorization reads, its availability is now load-bearing. Measured with the router scaled to zero:

~FailOpen explicit chat 200, auto 404 — but a medium-tier caller asking for kimi-k3 was served it (HTTP 200): no filter could name the model
✓FailClosed all chat 500, no bypass; embeddings and reranking unaffected

FailOpen would keep the Semantic router unavailable row identical across all three stacks, at the price of dropping the tier check during an outage. FailClosed is the one shipped — BBR already carries it for the same reason, and the router has taken over BBR's job on this path — so that row now reads explicit 500 / auto 500 here against explicit 200 / auto 404 elsewhere. A comparison row that differs honestly beats one that matches by hiding something.

A PostRouting BBR pass was tried as a way to have both: run the router before routing for the pool, then BBR before authorization to restore the model name. Authorization does not see that filter's header mutation, so it does not work.

08Whose model does the gate judge?

Once the router resolves auto before authorization runs, the tier check stops being about what the client asked for. It is about what the router picked — and the client cannot see the difference from the request it sent.

Dave has a medium tier ceiling. His org and team are irrelevant to model access. He sends the same three-field body every time:

POST /v1/chat/completions
{"model": "auto", "messages": [{"role": "user", "content": "…"}]}

Only the prompt text changes. The outcome does too:

dave’s prompt router picks Envoy agentgateway Kuadrant
“prove … irrational” kimi-k3 (B300) 403 403 403
“refactor this python function” deepseek-v4-flash 200 200 200
“hello there, good morning” qwen3.8-27b not run 200 200
Carol and Alice have a big tier ceiling and return 200 on all three prompts on all three stacks. Kuadrant measured over two warm passes.

The mechanism is the same one that makes pool routing work. Authorization reads x-gateway-model-name, and by the time it runs that header holds the resolved model — BBR derived it from the body the router rewrote on Envoy and Kuadrant, and the pre-routing transformation copied it from x-selected-model on agentgateway. There is no point in any of the three chains where a filter still knows the client said auto.

That is arguably correct: a tier is a ceiling, not a suggestion, and a caller should not reach a higher tier by asking indirectly. But consider what it looks like from dave’s side. He never named kimi-k3. He asked a question, and got:

✕403 · "the token tier does not allow the resolved model tier"

Which model caused the higher tier, and what he could have asked for instead, are not in the answer. Nothing in his request predicts it, and nothing in the response tells him what to retry with.

Open design question

Three ways to resolve it, in ascending cost

Make the denial actionable. Name the tier and an allowed alternative in the message. All three stacks already carry a configurable string here — Kuadrant's unauthorized.message, and the equivalents on the other two. Cheapest, and it turns a dead end into a retry.

Degrade instead of denying. Give the router a tier-aware model set so it never selects a tier the caller cannot reach. This is the behaviour most people assume auto already has. It needs the caller's identity at the router, which none of the three stacks currently passes to it.

Leave it. Defensible, and the current state. Worth being a decision rather than a side effect of where the filters sit.

09What the trace turned up

Reading the Kuadrant route configuration to write section 04 explained a failure that had been sitting in the comparison results unexplained.

The saved Kuadrant column carried this, in two consecutive runs:

✕auto_models: kimi-k3 / deepseek-v4-flash / qwen3.8-27b;
forged-header probe failed (HTTP 404, model None, upstream None)

The probe sends {"model": "auto"} together with a forged x-gateway-model-name: qwen3.8-27b and asserts that the semantic router still runs. Dumping the live route table showed why it did not: the ai.gateway.semantic_router per-route override was present on the chat route and on none of the five model routes, even though the manifest lists all six.

The object in the cluster had one HTTP_ROUTE patch; the file in the branch has six. The cluster copy predated the change and had never been re-applied. With the override missing, the forged header steered the first match onto model-qwen3-8-27b, where the router was disabled by the virtual-host default; model: auto then reached BBR untouched, no rule matched auto, the fallback route carried the literal string upstream, and the fixture answered 404 for a model it does not serve.

Re-applying the manifest and re-running the exact probe returned HTTP 200, model kimi-k3, upstream kimi-k3. The manifests were right the whole time; the retained cluster was stale.

A second trusted header that wasn’t

Automated review on the pull request raised a P2 against the transformation above, and it was right. The first arm originally read:

✕- condition: '"x-selected-model" in request.headers'
✓- condition: 'request.method == "POST" && request.path == "/v1/chat/completions" && "x-selected-model" in request.headers'

The reasoning behind the original was that x-selected-model comes from the semantic router, and the router overwrites a client-supplied value — which is measured and true. But that only holds on the chat path, because chat is the only path the router runs on. On /v1/embeddings and /v1/rerank the request goes to BBR instead, and BBR sets x-gateway-model-name from the body without stripping an unrelated inbound header. The unscoped arm then copied the client’s value straight over BBR’s.

A client choosing its own accelerator pool — the exact thing the shared route contract exists to prevent.

Not a privilege escalation: the big-tier authorization rule reads x-gateway-model-name, and forging a big-tier value into it gets the caller denied rather than admitted. The damage is misrouting, and it reads as an ordinary 404 or a quiet fallback to the CPU fixture rather than as a routing defect.

The pattern is worth naming, because it is the third time in this page: a header is only trustworthy on the path where the thing that sets it actually runs. Guarded now in two places — the offline validator rejects any transformation arm that writes the routing header without being scoped to chat, and the comparison sends a forged x-selected-model at /v1/rerank on every run, on all three stacks.

Worth keeping

The probe was doing its job

A stale filter that silently disables semantic routing on five of six chat rules produces no error, no failing status condition, and a perfectly ordinary-looking 404 from the upstream. It was visible only because the comparison asserts the router still runs when a client forges the routing header — and because that assertion writes its failure into a row someone reads.

Filter chains read from /config_dump on ai-gw-envoy and ai-gw-kuadrant; header deltas echoed by the KServe mock runtime; status codes and bodies from live calls to all three clusters on 2026-08-27. agentgateway's intra-route order is derived from its policy definitions, with four boundaries measured directly, as noted in section 03.

The agentgateway change in section 07 is verified across the full install → teardown → reinstall cycle, guarded by five negative-tested offline checks in validate-router-config.py, and recorded by re-running the comparison rather than editing its table by hand.
